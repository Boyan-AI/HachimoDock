桌面端 · Tauri 2 + React设备端 · ESP32-P4通信 · USB文档依据 · 0.1.101 / 0.7.72-p4
先明确目标：本教程把“实现”理解为复刻并运行当前仓库的完整作品。仓库包含客户端和固件源码；PCB、BOM、外壳与装配资料在 OSHWHub 硬件复刻页。如果你只想改软件，可以跳到第 5 步。

它是怎样工作的？

电脑上的 Agent 工作状态经 Bridge 汇总，由客户端通过 USB 发给设备；设备把状态画成宠物动画和 Session 气泡。设备按键与语音事件沿反方向送回电脑。

第一阶段

先做出可用成品

前四步优先使用发布包。你能更快确认硬件、屏幕、USB 和 Agent 跟随确实工作，之后再处理复杂的编译环境。

01

从硬件资料确认购物清单

先确认板、屏、输入和供电，暂时不用打样自制 PCB。

  1. 打开 硬件复刻页，逐项核对 PCB、BOM、接线和外壳资料。
  2. 准备 ESP32-P4 主板、适配的 2.8 英寸 480×640 MIPI-DSI 屏、USB 数据线；按 BOM 再准备三个按键、摇杆和音频器件。
  3. 第一次联调可以先用杜邦线；确认工作后再考虑定制 PCB 与外壳。
屏幕排线接 DSI 显示接口，不接 CSI 摄像头接口；插拔排线前先断电。接口、电压和排线定义必须和硬件资料一致。
依据：硬件方案硬件端资料
02

查明 ESP32-P4 芯片版本

完整烧录包分 v1 和 v3，选择依据是芯片修订版，不是电脑系统。

  1. 通过 USB 串口运行下面的只读脚本查询真实修订版，空白板也适用。查询前关闭占用串口的 Pet Manager；macOS 的端口通常是 /dev/cu.usbserial-… 或 /dev/cu.usbmodem…，Windows 在设备管理器查看 COM 编号。
  2. 芯片旧版 0.1～1.99 对应 v1 包；芯片 3.0～3.99 对应 v3 包。记录查询输出后，再打开 最新 Release 下载匹配的完整烧录包。

已安装的新固件会向客户端报告 chipRevision，用于自动选择升级镜像；当前设备诊断弹窗没有直接显示这个字段。要查看确切版本，仍用下面的串口查询。

准备 Python 3.10+，在独立 Python 环境安装项目指定的 esptool 5.4.0。从仓库根目录运行已附带的 只读查询脚本，把示例端口换成自己的。脚本不擦除或写入 Flash。

python -m pip install esptool==5.4.0
# macOS 示例
python firmware/tools/chip_revision/check_p4_revision.py --port /dev/cu.usbserial-0001
# Windows PowerShell 示例
python firmware/tools/chip_revision/check_p4_revision.py --port COM3
“ESP32-P4-WIFI6-M”里的 M 不表示 v3。版本不明时先停在此步确认，不能互刷，也不要使用 --force 绕过检查。
依据：只读查询脚本烧录前芯片检查源码设备诊断协议固件构建与烧录发布清单
03

按发布包指南烧录并首启

新设备使用完整出厂镜像；已有设备日常升级使用客户端。

  1. 解压第 2 步下载的完整烧录 ZIP，先读包内中文烧录指南。
  2. 确认设备是新机或明确需要恢复出厂，再按包内工具步骤连接 USB、核对芯片并烧录。
  3. 等待烧录完成和设备重启，检查屏幕是否亮起、默认形象是否播放。

包内脚本需要 Python 3.10+，会安装并检查 esptool 5.4.0。完整镜像包含 Bootloader、应用、默认形象和组件；单独的 firmware.bin 不是完整出厂镜像。

完整出厂烧录会覆盖设备已有设置、形象和组件。先备份现有设备数据；烧录中不要拔线。版本不符时不要继续。
依据：固件构建与烧录固件说明
04

安装 Pet Manager 并完成一次联调

先验证 USB 连接、状态气泡和实体输入，再尝试语音或生成服务。

  1. 在同一 Release 下载 macOS Apple silicon DMG 或 Windows x64 安装包，安装并打开 Pet Manager。
  2. 通过 USB 数据线连接设备，确认首页出现 ESP32-P4 设备、固件版本和连接状态。
  3. 启动一个受支持的 Agent（例如 Codex 或 Claude），开启实际任务，观察设备的宠物状态与 Session 气泡变化；再试一个按键操作。
  4. 需要语音识别、实时对话或形象生成时，才到客户端“API 配置”填写自己的服务凭据。

设备状态同步走 USB；PC 客户端需要保持运行。部分 Agent 的桌面会话切换能力有平台限制，先以状态显示成功作为首个里程碑。

依据：快速开始Agent 接入说明安全说明

05

从源码跑起网页界面

先熟悉 React 界面，构建成功后再碰原生依赖。

准备 Git LFS 和 Node.js 22+。在仓库根目录打开终端：

# 仓库根目录
git lfs pull
cd pc
npm ci
npm test
npm run test:bridge
npm run build:web
npm run dev:web

终端显示本地地址后在浏览器打开。这里能看界面、改 CSS 和 React；设备、系统权限与本机 Agent 功能必须在第 6 步的完整客户端中验证。

06

运行完整 Tauri 客户端

把网页界面和 Rust、Bridge、USB 串起来。

另需 Rust stable、目标系统的 Tauri 依赖，以及项目要求的可重定位 Node.js 与 FFmpeg 资源。先按 运行时依赖文档准备，再在 pc 目录执行：

07

构建对应芯片的固件

先跑主机测试，再编译；编译成功不等于真机全部验收。

准备 Python 3.10+、Git LFS，并在独立 Python 环境安装 PlatformIO Core 6.1.19、pytest、Pillow。首次构建会下载 ESP-IDF 与工具链。

# 仓库根目录；安装依赖前请先激活独立 Python 环境
python -m pip install platformio==6.1.19 pytest Pillow
git lfs pull
python firmware/tools/build_builtin_bundle.py --check
python -m pytest firmware/tests
cd firmware
# 按第 2 步确认的芯片，只选对应环境
python -m platformio run -e esp32_p4_evboard
# v3 芯片改用：python -m platformio run -e esp32_p4_evboard_v3

v1 环境使用 ESP-IDF 5.5.1，v3 使用 5.5.4；两个环境要顺序构建。需要制作完整出厂包时，再按 构建指南的 factory 章节执行，不能把仅应用分区镜像当出厂镜像。

pet_p4_main.c设备初始化与任务入口pet_p4_protocol.c设备消息处理pet_p4_renderer.c画面渲染pet_p4_input.c按键与摇杆输入

08

做一个可验证的小改动

建议从界面文案或样式入手，再逐步进入协议和固件。

  1. 在 DeviceDashboard.jsx 或相关组件中找到一个想改善的提示文案，先记录原文与预期。
  2. 只改这一处，并按仓库规范给新增或实质修改的代码结构写中文注释；若涉及公开行为，同步检查文档。
  3. 运行 npm test 和 npm run build:web，再用第 5 步网页预览；涉及 USB 或 Agent 行为时，还要用第 6 步原生客户端验证。
  4. 读懂一条实际状态链路后，再考虑改协议：Agent 适配器 → Session 同步 → Tauri/USB → 设备协议 → 固件渲染。
第一次修改不要同时碰硬件引脚、分区表、OTA 与 USB 协议。它们横跨 PC 和固件，验证成本明显更高。
依据：设备首页源码Session FeedUSB 协议
